The printed-equals-applied check is load-bearing on the rewritten text
======================================================================

VER-MOK-004 acceptance scenario 3 asks for the equality between printed and applied
defaults to be shown by making it fail, in both directions, and for the coverage
totality property to be shown the same way. VREC-MOK-004 recorded three such
divergences against the PREVIOUS twelve-then-thirty-eight-line text. This work order
restructured that text, which is precisely the change that could leave the tests
passing while no longer reading the thing they name. So all three were re-run against
the rewritten text rather than cited from the earlier record.

Each scratch change was made with an editor, run, and reverted individually. None is
in the commit; the confirmation is at the bottom of this file.

Reading
-------
A fails six tests because moving an applied default moves it for every test that
asserts a parsed configuration, not only for the equality test. The equality test is
among the six and is the one that says WHY in words: "the help states 100 as the
default for --ticks, which is not the value the program applies when --ticks is
omitted".

B is the stronger of the two directions and the reason it is run: moving the PRINTED
default alone fails exactly one test of eighteen, the equality test, naming --seed and
the wrong value. Seventeen tests pass, so no other test in the file would have caught
a help text that lies about a default. Without this check the drift would be silent.

C fails exactly one test, the coverage-totality test, which prints both sorted lists
side by side so the surplus option is visible without reading the source. This is the
check that a future option added to the parser and not to the help cannot pass.
