`SPEC-MOK-004` rule 6 records the observer's interface as **94 items, 118 `pub` lines and 24 public
fields**. `SPEC-MOK-002` rule 5 lists the engine's items by hand and records no total. Act 3
corrects rule 9, rule 10 and rule 11 and corrects **nothing in rule 6**, and this file is the
measurement behind that non-correction. A figure left alone still has to be shown to hold.

Six enumerations: both packages at both parents and at the merge. The parents are measured because
the merge is the first tree in which Phase 4a's record stream and master's social source both
exist, and rule 6 is a figure about a tree, not about a diff.

Part 1 — the observer: master's interface, and master's source
--------------------------------------------------------------

Against master the observer's enumeration is byte-identical, zero differing lines. That is stronger
than the totals matching, and the reason it holds is stronger still:

    git diff --stat fa065cc HEAD -- mokiterions-tui/src/
    (no output)   EVERY OBSERVER SOURCE FILE AT THE MERGE IS MASTER'S, BYTE FOR BYTE

    git diff --stat ff3a155 fa0bfd9 -- mokiterions-tui/src/
    (no output)   PHASE 4A TOUCHED NO OBSERVER SOURCE FILE

The second command is what makes the first safe rather than alarming. A merge that resolves an
entire source directory in one parent's favour is exactly the shape in which the other parent's
work is silently lost — five observer files differ between the branch and the merge, 503 insertions
and 100 deletions, and read alone that looks like 503 lines the merge threw away. Measured against
the merge base, the branch's observer *is* the base's observer: Phase 4a adds a record stream the
observer does not read, so those 503 lines are master's arrivals, the branch never had them, and
taking master's copy wholesale loses nothing. `census-reconciliation.txt` says the same thing from
the test side — the observer's ten targets are unchanged at 142 — and this is the source-side form
of it.

The `USAGE` constant is one `pub const` before and one `pub const` after; its type, name and

Against the branch:

    50c50
    < simulation.rs  item  pub const ALL: [Self; 12] = [
    ---
    > simulation.rs  item  pub const ALL: [Self; 15] = [

Master's contribution, and it is `EventType::ALL` at `simulation.rs:1337`. Twelve event kinds became
fifteen when master added `attack_resolved`, `threat_resolved` and `surrender_resolved`. The
declaration is one `pub const` before and after and the array's length is part of its rendered type,
which is why a purely additive change to a closed domain shows up as a changed line rather than as
three new items.

This is the single most consequential line in this file for what act 3 leaves undone. Phase 4a's
`SPEC-MOK-006` specifies a record for each event kind and was written against twelve; the merge has
fifteen. The engine's own test `every_event_kind_has_its_exact_record_shape` passes at the merge —
`gates.txt` records 298 of 298 — because it reads `EventType::ALL` and the code covers all fifteen.
The specification is what does not. The `SPEC-MOK-006` amendment carried to the owner alongside this
packet is drafted from that gap, and `README.md` states it as a finding rather than leaving it to be
inferred from a diff line.

`Config` gains no public field on any of the three trees: 43 public fields, master, branch and merge.
The sink reaches the engine as a `Write` the caller owns and never as a path, which is what makes
`SPEC-MOK-006` rule 5.4's "no path among the header's nine fields" a property of the type rather
than a discipline. `gates.txt` records the runtime form of the same fact — no record carries a path.

Reconciliation with SPEC-MOK-004 rule 6's recorded 94 / 118 / 24

    mechanical items      101  -  7 `pub mod` =   94   = rule 6's Total
    mechanical pub lines  125  -  7           =  118   = rule 6's same interface counted by line
    mechanical fields      24                 =   24   = rule 6's stated field figure

The seven are `lib.rs`'s `pub mod authority;` through `pub mod state;`, visible under `lib.rs` in
every observer enumeration below. Rule 6's "What is counted" list enumerates the seven presentation
modules' members and does not count the module tree; the enumerator's item pattern does. The field
figure needs no adjustment because a `pub mod` declaration is not a field.

What this rules out, because the wrong reading is available: `101 ≠ 94` is not seven items that
entered at some point and were never recorded. The seven are named, they are `pub mod` lines, they
are present at all eight revisions in Part 3, and subtracting them reproduces the recorded figure
exactly on two independent counts — items and lines. A coincidence does not do that twice.

`SPEC-MOK-004` rule 6 is correct at the merge and act 3 does not touch it.
