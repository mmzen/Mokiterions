1. No engine name appears anywhere in `mokiterions-tui`, tests included
-----------------------------------------------------------------------

    grep -rnE '\b(Zug|Krul|Quib|Sput|Trok|Womp|Hozz|Nurb|Vonk|Gorm|Xob|Drix)\b' mokiterions-tui/

    (no match)

This is VER-MOK-011's static row in full, including its clause about "its tests' fixtures where
they stand in for engine records". Two fixtures held engine names when the implementation was
first written and no longer do:

  * `mokiterions-tui/tests/spatial.rs::glyphs_are_the_assigned_ones` listed the twelve names
    against their twelve glyphs. That table is exactly what REQ-MOK-041 forbids the observer to
    hold, and its own doc comment claimed it was not there. It now asserts the derivation over
    every initial a name can carry -- for each of the twenty-six ASCII letters, in either case and
    at one, four and five characters, the glyph is that character uppercased -- and that the
    twenty-six initials give twenty-six distinct glyphs. That subsumes the twelve without holding
    them: twelve names with twelve distinct initials draw twelve distinct glyphs. The boundary case
    `agent_glyph("") == '?'` is asserted as before.

  * `mokiterions-tui/src/render.rs`'s inline tests passed names to `entry_lines`. Three call it:
    the two pre-existing cases `the_bar_row_reproduces_the_specified_form` and
    `a_zero_value_is_a_zero_and_an_absent_value_is_a_dash`, which gained an argument because the
    function gained a parameter, and this work order's new
    `an_entry_carries_the_name_before_the_identifier_and_takes_six_columns`. All three now pass
    fabricated stand-ins -- `"O"`, `"Ort"`, `"Blip"`, `"Weeee"`, one per admissible length -- and
    the assertion against SPEC-MOK-003 rule 4's mockup columns reads
    `"Blip  M05  A  81:14         "` where the specification's mockup prints a name beside `M05`.
    What the six-column field has to hold is a length, not a particular name, so the substitution
    weakens no assertion; the comment at that assertion says so and says why. No assertion of
    either pre-existing case changed: each gained an argument and nothing else.

Where an observer test needs the name a subject actually has, it reads it from the records rather
than from a fixture:

  * `mokiterions-tui/tests/verification.rs` reads names through the already-public
    `Observer::events`, via its `reported_names` helper;
  * `mokiterions-tui/src/verification.rs:701` reads `observer.name_of("M01")` to form the expected
    glyph for the shared-cell case, so the expectation comes from the engine's report and not from
    the identifier.

There is therefore no revision of `SPEC-MOK-001`'s name table that could make an observer test
pass while a frame drew the wrong name.

---------------------------------------

    spatial.rs:123,128,129,134,136,137     `Viewport::dot_of` and `Viewport::bounds`

Those six lines are the pre-existing canvas geometry that ratatui's canvas requires, unchanged by
this work order. `agent_glyph`, `name_of`, `entry_lines` and the inspector heading are integer and

strings the search also turns up (`"0.75"`, `"0.02"`, `"1.50"`) are the density argument's text
form, parsed to an integer percentage, and predate naming.
