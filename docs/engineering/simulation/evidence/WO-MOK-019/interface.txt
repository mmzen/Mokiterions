Part 1 — the engine: one changed line in ninety-two, and it is rule 4's parameter
--------------------------------------------------------------------------------

    4c4
    < lib.rs           item  pub fn execute<I, S, W, E>(args: I, stdout: &mut W, stderr: &mut E) -> u8
    ---
    > lib.rs           item  pub fn execute<I, S, W, E>(

That is the whole diff. `execute` gained the fourth parameter SPEC-MOK-002 rule 4 states —
`records: Option<&mut dyn Write>` — and the signature therefore no longer fits one line:

    pub fn execute<I, S, W, E>(
        args: I,
        stdout: &mut W,
        stderr: &mut E,
        records: Option<&mut dyn Write>,
    ) -> u8
    where
        I: IntoIterator<Item = S>,
        S: Into<String>,
        W: Write,
        E: Write,

**What the mechanical figure cannot see, stated before what it can.** `interface.py` renders the
first line of each item, so a signature that spills across lines is reported as a stub and the
parameter list is invisible to it. On this one item the enumeration is therefore weaker after the
change than before, and no reading of the figure `49 / 43 / 92` establishes anything about the
parameter. This is not a defect discovered here: SPEC-MOK-002 rule 5's 2026-08-20 amendment
anticipated it and replaced the single grep with two, "Because the signature now spans several
lines". The two greps are the check for this item, and the enumeration is the check for the rest.

    $ grep -n 'pub fn execute' src/lib.rs
    54:pub fn execute<I, S, W, E>(
    (exactly one line)

    $ grep -n 'records: Option<&mut dyn Write>' src/lib.rs
    58:    records: Option<&mut dyn Write>,
    (exactly one line)

The first fails on a second public process-boundary function; the second fails on a fifth
parameter, a second sink, or a sink that is not optional. Both return exactly one line, which is
rule 5's restated form satisfied literally.

**What the figure does establish, which the greps cannot.** A parameter is not an item, so the
interface grows by no item — but that sentence is a claim about the whole surface, not about
`execute`, and the enumeration is what measures it. Item for item, across ninety-two `pub` lines:

    no `pub struct`, `pub enum`, `pub trait`, `pub fn` or `pub const` entered or left  (49 = 49)
    no public field entered or left                                                   (43 = 43)
    no item's rendered declaration changed, save the one line above                   (92 = 92)

Named, because two of them are the ones a sink option would most plausibly have moved:

    cli::Command      pre and post   `enum Command { Help, Run(Config) }`, unchanged
    simulation::Config  43 public fields across all types, unchanged; Config gains none

`Config` gaining no field is the substantive fact rather than a bookkeeping one. The sink reaches
the engine as a `Write` the caller owns, never as a path, so there is no public field for a
destination to sit in — which is what makes SPEC-MOK-006 rule 5.4's "no path among the header's
nine fields" a property of the type rather than a discipline applied at the point of writing. The
engine cannot state a path it was never given.

Two of the forty-nine items are `lib.rs`'s `pub mod cli;` and `pub mod simulation;`. They are the
module tree rather than members of the interface, and they are counted here because the tool counts
them; rule 5 records no total, so unlike the observer's figure nothing needs adjusting for them.

**Mutating methods: still exactly two, and the carrier that takes the sink is not one of them.**

    $ grep -n 'pub fn .*&mut self' src/simulation.rs
    1533:    pub fn run<W: Write>(&mut self, output: &mut W) -> io::Result<RunSummary> {
    1626:    pub fn advance_tick(&mut self) -> Result<TickOutcome, String> {

`run` and `advance_tick`, which is what rule 5 states. The sink is carried down the same call chain
the text stream travels, and the method that takes it is

    $ grep -n 'pub(crate) fn run_recording' src/simulation.rs
    1545:    pub(crate) fn run_recording<W: Write>(

which the pattern does not match because `pub(crate) fn` is not `pub fn`. Rule 5's amendment names
this explicitly so that the non-match is disclosed rather than relied on silently, and the
disclosure is discharged here by measurement: `run_recording` does not appear in the ninety-two-line
enumeration above, so it is not on the interface, and no enumerated item returns it, takes it or
names it. `Simulation::run`'s own enumerated form — `&mut self` and a writer in, `io::Result<RunSummary>`
out — is byte-identical at both revisions, and it delegates to `run_recording` with no sink.


Part 2 — SPEC-MOK-002 rule 6 re-checked rather than amended
-----------------------------------------------------------

Rule 6 carries a 2026-08-20 note recording that it is deliberately **not** amended by this work
order. A rule that is not amended still has to be shown to hold, so each of its five properties is
measured at the candidate tree.

(a) **No public item permits mutation of engine-owned state.** The two `&mut self` methods are
    `run` and `advance_tick`, measured in Part 1. Both take `&mut self` on a `Simulation` the
    caller owns, which rule 6's 2026-08-18 amendment settles as not a handle into another owner's
    state. This is one measurement serving two rules, and it is recorded once.

(b) **No public item hands out a borrow of, or a reference into, engine-owned state.**

        $ grep -n 'pub fn .*-> *&' src/simulation.rs src/cli.rs src/lib.rs
        src/simulation.rs:1033:    pub fn as_str(self) -> &'static str {
        (one line)

        $ grep -n 'pub fn .*-> *impl' src/simulation.rs src/cli.rs src/lib.rs
        (no output: no public item returns an iterator or an opaque type)

        $ grep -n 'pub [a-z_]*: *&' src/simulation.rs
        (no output: no public field is of reference type)

    The single returner of a reference is `EventType::as_str`, whose `&'static str` is a string
    literal in the binary and not a borrow of anything the engine owns. Every other public item
    returns an owned value, which is the shape rule 5's snapshots have and rule 6's amendment
    admits.

(c) **No interior mutability anywhere in the engine.**

        $ grep -c 'Cell<\|RefCell<\|Rc<\|Arc<\|Mutex<\|RwLock<\|Atomic' src/simulation.rs src/cli.rs src/lib.rs
        src/simulation.rs:0
        src/cli.rs:0
        src/lib.rs:0

    So no `&self` method can mutate, and (b) cannot be circumvented by an interior-mutable value.

(d) **The ten prohibited names are ten, and every one is private.** Each declaration, with its
    visibility as written:

        Mokiterion            401:struct Mokiterion {
        Food                  394:struct Food {
        RelativeDirection     285:enum RelativeDirection {
        ActionResult          954:struct ActionResult {
        Observation           518:struct Observation {
        PerceivedFood         501:struct PerceivedFood {
        PerceivedMokiterion   511:struct PerceivedMokiterion {
        SplitMix64            867:struct SplitMix64 {
        DecisionEntropy       707:struct DecisionEntropy<'a> {
        DecisionSource        723:trait DecisionSource {

    Not one carries `pub` or `pub(crate)`. `SplitMix64` is the one this work order touches: the
    record projection reads its state through a `#[cfg(test)]` accessor returning an owned `u64`,
    so the value crosses and the type does not, and the type stays private in every build
    configuration. `Observation` and `DecisionSource` are the two that carry the ADR-MOK-001 trust
    boundary and neither is touched at all. This is an enumeration of every declaration rather than
    a search for `pub` before each name: a positive enumeration cannot pass by failing to look.

(e) **The four counter fields this work order adds are private, and the type exposes no accessor
    for any of them.**

        crossings: u64,
        consumed: [u64; 3],
        regenerated: u64,
        regeneration_skipped: [u64; 2],

    Four fields carrying seven counters. None is `pub`, so none appears among the forty-three
    public fields of Part 1, and the enumeration is what establishes that rather than a promise:
    a field widened to `pub` would have made the figure forty-four. The `#[cfg(test)]` entropy
    accessor at simulation.rs:2506 is likewise absent from the enumeration, because
    `interface.py` skips `#[cfg(test)]` bodies whole and because the accessor is not `pub`
    either way. `static-checks.txt` items 8, 9 and 11 carry the same three facts approached from
    the other side — from the private items the internal tier reaches for — and the two agree.

Rule 6 is the security-relevant rule of SPEC-MOK-002. Nothing it prohibits became public, and
nothing public became a path to anything it prohibits.

Reconciliation with SPEC-MOK-004 rule 6's recorded 94 / 118 / 24
----------------------------------------------------------------

The mechanical figure is 101 items and 125 `pub` lines; the rule records 94 and 118. The difference
is a counting convention, documented, and not drift. Rule 6's "What is counted" list enumerates the
seven presentation modules' members and does not count `lib.rs`'s seven `pub mod` declarations,
which are the module tree; `interface.py`'s item pattern does count them. WO-MOK-011/interface.txt
line 60 states the adjustment, and it is quoted here rather than re-derived:

    mechanical items 101 − 7 `pub mod` =  94   = rule 6's Total
    mechanical pub lines 125 − 7       = 118   = rule 6's "same interface counted the other way"
    mechanical public fields            24     = rule 6's stated field figure

Both differences are the same seven lines, and the field figure needs no adjustment because a
`pub mod` declaration is not a field. The seven declarations are visible in the retained
enumeration at `lib.rs item pub mod authority;` through `lib.rs item pub mod state;`.

It is worth saying plainly what this rules out, because the alternative reading is available and
wrong. `101 ≠ 94` is not an interface that grew by seven items at some point and was never
recorded. The seven are named, they are `pub mod` lines, they exist at all five revisions above,
and subtracting them gives the recorded figure exactly on two independent counts — items and
lines — which a coincidence would not do. SPEC-MOK-004 rule 6 records the observer's interface
correctly and needs no correction under this work order.

Rule 11 of the same specification is a different matter: it records the *test census*, not the
interface, and its figures do move from 212 to 246. That correction is `analysis/census-reconciliation.txt`'s
subject and is disclosed in `completion-summary.md`.
