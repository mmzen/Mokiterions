REQ-MOK-060 fixes where its correction may be made and where it may not, and calls that constraint
"the load-bearing part of this requirement, because it is what keeps INT-MOK-010's promise that
baseline reproduces byte-identically." The permitted place is the waste condition of the two proposing
sources -- rule 5's `satiety + restoration <= 100` and rule 19's tolerant `S + R - 100 <= T * R / 100`.
The forbidden places are rule 16's uniform class selection, rule 15's regeneration amount, rule 9's
eat effect and the food table's restoration values, each because it is world behaviour under every
policy and would therefore move a `baseline` run.

**This file measures both lists, and both are unchanged.** The forbidden four are unchanged because the
constraint holds. The permitted two are unchanged because REQ-MOK-060 is unimplemented under the product
owner's approved deferral of 2026-08-20, so the correction that was licensed to touch them has not been
written. Section 4 says so plainly rather than presenting the second result as a virtue.


1. Why a diff of the file cannot answer this
---------------------------------------------

mokiterions-core/src/simulation.rs goes from 4,180 lines to 6,865 between the two commits. Every region
named above therefore moves, some by hundreds of lines:

    rule 9's eat effect      1901-1944  ->  2322-2365
    rule 15's regeneration   2036-2096  ->  2873-2933
    the food table            337-381   ->   397-441
    rule 4's source           716-732   ->   897-913

    $ git diff --stat 39662d13..1b06d851 -- mokiterions-core/src/simulation.rs
     mokiterions-core/src/simulation.rs | 2999 +++++++++++++++++++++++++++++++++--
     1 file changed, 2842 insertions(+), 157 deletions(-)

A whole-file diff reports that movement. It cannot state that a region is unchanged, because a region
that moved intact and a region that moved and was edited look the same in a diff that has to realign
2,842 inserted lines around them. So the comparison is done the other way round: each region is lifted
out by name at both commits and the two extracts are compared as text.

analysis/regions.py is that reader, retained here. A region is named by the exact source line that opens
it -- never by a line number, so one region table serves both commits -- and is taken as the
brace-balanced item from that line, or as the span between two such lines. **The comparison is on the
raw extracted bytes**: no comment stripping, no whitespace folding, no reformatting. That is the
strongest reading of "line for line", and the only one that needs no argument about what a
normalization discarded.

The reader carries an expectation per region and exits non-zero if any region fails it. Three regions
this work order does change are in the table as controls, expected to differ. Without them a run
reporting "same" everywhere would be worth nothing, because a broken extractor reports that too.

    $ git show 39662d13:mokiterions-core/src/simulation.rs > base.rs
    $ git show 1b06d851:mokiterions-core/src/simulation.rs > head.rs
    $ python analysis/regions.py base.rs head.rs
    exit 0

3. The thirteen forbidden regions, and what each rule being unchanged buys
--------------------------------------------------------------------------

**The food table's restoration values.** `FoodClass`, its `restoration` and `calorie_rank` tables, its
display and the `Food` record: four regions, 1,137 bytes, all identical.

    fn restoration(self) -> (u8, u8) {
        match self {
            Self::Low => (15, 5),
            Self::Medium => (30, 10),
            Self::High => (50, 20),
        }
    }

Those six numbers are what REQ-MOK-060's own rationale identifies as the mechanism it wants to correct:
a high-class resource restores 50, so the non-waste condition makes it eatable only at satiety of at
most 50, and what is passed over stays standing. Moving any of them would have been the direct fix and
is exactly what the requirement forbids, because rule 9 applies them under every policy.

**Rule 9's eat effect.** One region, the whole `Action::Eat` arm of `apply_action`, 44 lines and 1,911
bytes, identical. It removes the resource, reads `restoration()`, saturates each attribute and clips at
`ATTRIBUTE_MAX`, and emits `FoodConsumed` with both before-and-after pairs. Every byte of that is shared
by all four sources.

**Rule 15's regeneration amount and rule 16's class selection.** `regenerate_food` is one 61-line
function holding both, 2,179 bytes, identical, together with `REGENERATION_INTERVAL = 10` and
`REGENERATION_YIELD = 2`, `RegenerationSkipReason` and its display, and `food_counts`.

Rule 16 is the region with the widest blast radius and the reason is not composition at all:
"[it] would additionally risk moving the shared entropy stream's consumption, which diverges
everything." One extra or missing draw in a regeneration opportunity shifts every later draw in the run,
so a change there would diverge all 90 baseline cells and every capture any earlier work order retained.
That it is byte-identical is what post/byte-identity.txt's 30 of 30 `baseline` cells rest on.

**Rule 14's timing.** Rule 14 is a timing rule, so the call site is in the table and not only the
function it calls:

        if self.tick.is_multiple_of(REGENERATION_INTERVAL) {
            for territory in Territory::ALL {
                self.regenerate_food(output, territory)?;
            }
        }

Five lines, 189 bytes, identical, and still positioned after the loop over scheduled agents. This is the
one region where a change was a live risk rather than a hypothetical: the lines immediately above it did
move, because rule 25's clearing of the suffered-attack record was inserted inside the agent loop. A
clearing placed a few lines lower would have landed between the loop and this block and changed nothing
here; a regeneration call moved a few lines higher would have run before the last agent's survival decay
and changed every tick divisible by ten. The block did not move relative to the loop, and comparing the
call site rather than only `regenerate_food` is what establishes that.

**Rule 4, which the requirement does not name but its argument depends on.** REQ-MOK-060 permits the
correction in the two waste conditions precisely because "rule 4's candidate list offers `eat` for each
co-located resource with no waste condition at all, so no relaxation of a waste condition can reach it."
That argument is only sound while rule 4 has no waste condition. `BaselineDecisionSource` and its
`DecisionSource` impl are in the table for that reason, 501 bytes across two regions, identical.


4. The two permitted waste conditions are also unchanged, and that is the deferral
----------------------------------------------------------------------------------

Rule 5's waste condition and rule 19's tolerant form are where REQ-MOK-060 licenses the correction.
Eight regions cover them -- the two predicates, the four selectors that apply them, `WASTE_TOLERANCE_MAX`
and `derive_waste_tolerance` -- and every one is byte-identical to the baseline.

    fn fits(&self, food: &PerceivedFood) -> bool {
        self.satiety.saturating_add(food.class.restoration().0) <= ATTRIBUTE_MAX
    }

    fn fits_within_tolerance(&self, food: &PerceivedFood) -> bool {
        let restored = u16::from(food.class.restoration().0);
        let resulting = u16::from(self.satiety) + restored;
        let maximum = u16::from(ATTRIBUTE_MAX);
        if resulting <= maximum {
            return true;
        }
        resulting - maximum <= u16::from(self.waste_tolerance) * restored / 100
    }

Both are the pre-change predicates exactly. **REQ-MOK-060 is unimplemented**, under the product owner's
approved deferral of 2026-08-20, recorded in escalation.md and in WO-MOK-016 at line 128. So this half
of the table is not evidence that the correction was confined; it is evidence that the correction was
not made. The requirement's ceiling fails in 14 of the 15 measured cells, escalation.md records that,
and composition.md is where the measurement is owed.

Stating it this way matters because the two halves of this file would otherwise read as one clean
result. The matrix row this file serves has two clauses -- "the change touches rule 5's and rule 19's
waste condition only" and "rule 4, rule 9's eat effect, the food table and rules 14 to 16 are
unchanged" -- and only the second is discharged here. The first is vacuously true at this commit, and a
vacuous truth recorded as a pass is the kind of thing this packet exists to prevent. When the deferred
amendment lands, the same reader re-run over the new commit will show some of the eight permitted regions
differing and all thirteen forbidden ones unchanged, and that run is the one that discharges the row.


5. What this file does not establish
-------------------------------------

- Nothing here is a verification verdict. VER-MOK-016 is the contract, VREC-MOK-016 the record.
- The region table is a list, and a list can omit. What bounds the omission is not this file but
  post/byte-identity.txt: all 30 `baseline` cells are byte-identical across the two commits,
  unprojected, so no world rule reachable under `baseline` moved -- whether or not it is named here.
  This file localizes that result to named rules; it does not carry it.
- Byte identity of a region is not behavioural identity of the rule. A caller could pass different
  arguments to an unchanged function. For rule 9 and rules 14 to 16 the callers are in the same tick
  loop and reached under every policy, which is what the `baseline` cells cover; for rule 4 the source
  is selected by `--policy baseline` and nothing else calls it.
- The 14-of-15 composition failure is stated here as context and is measured elsewhere. This file
  measures source text, not runs.
- `analysis/regions.py` counts braces outside string and character literals rather than parsing Rust.
  It is sound for the regions in its table, all of which are ordinary items, and it stops rather than
  guessing when an anchor matches no line or more than one.
