two workspace members are shortened to their directory names above; nothing else is edited.

Every crate but the two workspace members is a transitive dependency of ratatui, reached through
mokiterions-tui. None of them is reachable from the engine -- section 3 is that check.

`-D warnings` is the declared lint gate, and it is the only one: neither package declares a crate-level
lint attribute and neither manifest carries a [lints] table, so the gate lives in this command line and
nowhere else. That is why the command matters more here than in a repository that pins its lints in the
manifest, and why the next clause is worth measuring rather than asserting.

**No `allow` attribute was added and no lint was suppressed to accommodate this change.** Three exist in
the workspace, and all three predate the work order:

the engine, so the engine -- which is what this work order changes -- carries no suppression at all.


3. cargo tree -p Mokiterions
-----------------------------

    $ cargo tree -p Mokiterions
    Mokiterions v0.1.0 (mokiterions-core)
    exit 0

One line. The engine resolves to itself and to nothing else, which is what SPEC-MOK-002 rule 1 and
ARCH-MOK-001 as amended require with no exception, and what REQ-MOK-026 is discharged by. A dependency
shared with mokiterions-tui would appear here, and none does.

The engine's manifest is the source of that, and it is empty by declaration rather than by accident:

    [dependencies]
                    <- mokiterions-core/Cargo.toml, last line, no entry

There is no [dev-dependencies] table at all, which is the stronger form of the same claim: the 250
tests of section 4 are written against std and the crate under test, with no test-only crate anywhere.

For contrast, and because VER-MOK-016 asks for the observer's set in the same section:

    $ cargo tree -p mokiterions-tui --depth 1
    mokiterions-tui v0.1.0 (mokiterions-tui)
    |-- Mokiterions v0.1.0 (mokiterions-core)
    `-- ratatui v0.30.2

One path dependency on the engine and ratatui at the pinned 0.30.2, with `default-features = false` and
exactly the three features SPEC-MOK-003 fixes -- "crossterm", "layout-cache", "underline-color".
Nothing added. The arrow runs one way, engine to observer, which is the direction ARCH-MOK-001 fixes.


4. cargo test at the workspace root
------------------------------------

Retained whole rather than restated. Its figures, and where each log is:

    baseline/test-run.txt          39662d13   212 names   212 passed   exit 0
    post/test-run.txt              7c4aef39   249 names   246 passed   exit 101   3 failing
    post/test-run-amended.txt      13906153   250 names   250 passed   exit 0

The 3 failures at 7c4aef3 are the four unsatisfiable obligations escalation.md records; the amendment
of 2026-08-20 resolved them, and the amended log is the state of the branch. Both candidate pairs are
kept, for the reason post/test-census-reconciliation.md section 8 gives.

VER-MOK-016 asks that the one invocation reach "every tier of both packages ... with no feature,
environment variable, ignore attribute, extra command, terminal or working-directory dependence." Every
clause of that is measurable, and each is zero or nothing:

    $ grep -rn "#\[ignore" --include=*.rs mokiterions-core mokiterions-tui | wc -l
    0

    $ grep -rn "cfg(feature" --include=*.rs mokiterions-core mokiterions-tui | wc -l
    0
    $ grep -n "^\[features\]" mokiterions-core/Cargo.toml mokiterions-tui/Cargo.toml | wc -l
    0

    $ grep -rn "env::var\|env!(" --include=*.rs mokiterions-core/tests mokiterions-tui/tests
    (no match)

    $ grep -rn "CARGO_BIN_EXE\|current_dir\|process::Command" --include=*.rs \
          mokiterions-core/tests mokiterions-tui/tests
    (no match)

The last two are the load-bearing pair. A CLI test that spawns the built binary would depend on the
working directory and on the target directory's layout, and mokiterions-core/tests/cli.rs does not: it
calls `mokiterions::cli::parse` in process, as its own header states, and asserts on the returned
`Command`. No test in either package starts a process, reads an environment variable or names a path.
Terminal dependence is excluded by the same fact -- nothing in the tests opens a terminal, and the
observer's rendering tiers assert against a ratatui test backend rather than a tty.

The 250 names carry the target they ran in, so the "every tier" clause is checkable by reading
post/test-census-amended.txt rather than by trusting this sentence. Sixteen prefixes appear: the fifteen
integration targets of section 5 -- seven of the engine, eight of the observer -- and `unittests`, whose
rows carry the module path and cover four separate unit units:

    unittests :: simulation::…   82   the engine's library
    unittests :: render::…       18   the observer's library
    unittests :: verification::…  9   the observer's library
    unittests :: state::…         4   the observer's library
    unittests :: tests::…         8   the observer's binary

The engine's binary is the one compilation unit with no unit tier, and it is 19 lines that hold no
behaviour to test: it locks and buffers the two streams, calls `mokiterions::execute` with the arguments,
and turns a flush failure into exit 1. Every decision it could have made is in the library, where
mokiterions-core/tests/cli.rs and the 82 rows above reach it.


5. Packages, targets, build scripts and names
----------------------------------------------

VER-MOK-016: "No new package, no new target, no build script, and no change to any package, library or
binary name."

    $ git diff --stat 39662d13..1b06d851 -- Cargo.toml Cargo.lock \
          mokiterions-core/Cargo.toml mokiterions-tui/Cargo.toml
    (no output -- not one of the four files differs)

That single diff settles the package count, both target lists, all six names and the absence of a build
script at once, because every one of them is declared in those four files and in no other place. The
lock file is in the check deliberately: an added dependency that a manifest reached by inheritance
would still move Cargo.lock, and it did not move.

test files are the same fifteen at the baseline commit, by name:

    $ git ls-tree -r --name-only 39662d13 | grep -E '(mokiterions-core|mokiterions-tui)/tests/'

  is recorded with the toolchain version above for that reason.
- The three `allow(dead_code)` attributes are shown to be unchanged by this work order, not shown to be
  justified. They belong to the observer and to the work order that wrote them.
