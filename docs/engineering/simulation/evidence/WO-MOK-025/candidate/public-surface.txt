The engine's public interface, base against candidate
=====================================================

SPEC-MOK-002 rule 5 lists the engine's public interface item by item and rule 6 counts it.
This file is the measurement of what this work order added to it, and the run of rule 5's own
mechanical checks at the candidate. WO-MOK-025's completion report item 2 is what it serves.

Rule 5 names its files as src/lib.rs and src/simulation.rs, from before ADR-MOK-004 moved
each package under its own directory. Those paths are mokiterions-core/src/lib.rs and
mokiterions-core/src/simulation.rs here; nothing else about the checks changes.

sources at both revisions. It counts what rule 6 counts: a pub item, a public field, and the

Rule 5's DecisionRequest cell describes it as "an opaque value type of four owned or 'static
string parts, with per-part accessors returning &str and one accessor returning them in the

exactly them: shared_rules, actor, observation and permitted_set are the four parts, blocks
returns them in the composition order. So eight of the eleven arrivals are enumerated.

  THREE ARE NOT, AND A FOURTH ITEM IS NOT EITHER. DecisionRequest::tick,
  DecisionRequest::actor_id, ReplayPort and ReplayPort::new are outside every list rule 5

That is a finding of this work order, reported and not repaired. candidate/static-checks.txt
check 6 is the check that produced it and states the whole of the case: ReplayPort is
authorized in substance by ARCH-MOK-002, which places the transcript's parsing in the engine
package as ReplayPort, and it cannot be narrowed, because both hosts construct it -

12.1.1 opens the transcript in the host. tick and actor_id are a sixth and seventh accessor

reads all twelve added items one at a time and finds no transport type, no reference into
authoritative state and no mutable borrow handed out. WO-MOK-025 stop-and-escalate condition

--- Rule 5's mechanical checks, run at the candidate --------------------------------------

The three greps for execute, each of which must return exactly one line:

    grep -n 'pub fn execute' mokiterions-core/src/lib.rs
      87:pub fn execute<I, S, W, E>(

    grep -n 'records: Option<&mut dyn Write>' mokiterions-core/src/lib.rs
      91:    records: Option<&mut dyn Write>,

    grep -n 'port: Option<&mut dyn Proposer>' mokiterions-core/src/lib.rs
      92:    port: Option<&mut dyn Proposer>,

One line each. A sixth parameter, a second sink, a second port, a sink that is not optional
or a port that is not optional fails one of the last two; a second public process-boundary
function fails the first.

The third grep is the amendment ADR-MOK-007 authorized and this stage wrote. The 2026-08-20
restatement read "a fifth parameter ... fails the second", and the port on execute is that
fifth parameter, so a build that added the port and left that sentence standing would fail its
own specification. Rule 5 says so itself.

The two-door check:

    grep -n 'pub fn .*&mut self' mokiterions-core/src/simulation.rs
      3731:    pub fn run<W: Write>(&mut self, output: &mut W) -> io::Result<RunSummary> {
      3899:    pub fn advance_tick(&mut self, port: Option<&mut dyn Proposer>) -> Result<TickOutcome, String> {

Exactly run and advance_tick. Rule 5 attaches a second obligation to this check, that
advance_tick's signature is one line in the source, because a wrapped signature puts the
declaration keyword and the receiver on different lines and the pattern would then match
neither - reporting one door where there are two and passing while doing so. It is one line,
at 100 columns including its leading indentation, which is exactly rustfmt's default
max_width and there is no rustfmt.toml in this repository to change it. That is the reason the
trait is named Proposer rather than DecisionPort: rule 5 records that DecisionPort reaches 109
columns in this signature and 104 with the shortest sensible parameter name. The margin is
zero, so a future parameter on this method cannot be added within the limit, and rule 5's own
sentence covers that case - it must change this check's form in the same commit.

The pattern must also not appear in prose in that file. It does not; the two lines above are
the whole of the output, and rule 5 records that a documentation comment matched during this
stage's implementation and that the comment was reworded rather than the check loosened.

Interior mutability, which rule 5's paragraph on mutating methods rests on:

    grep -nE '\b(Cell|RefCell|Rc|Arc|Mutex|RwLock|Atomic[A-Za-z0-9]+)\b' \
        mokiterions-core/src/*.rs mokiterions-tui/src/*.rs | wc -l
      0

No engine type contains a Cell, a RefCell, an Rc, an Arc, a lock or an atomic, and neither
does the observer, so no &self method can mutate through one.

That is the whole of the product-code breakage: the engine's binary target and the observer,
and no others. The engine's own run path does not call the public advance_tick - run_recording
reaches the private step, and the public advance_tick delegates to the private
advance_tick_with_source - so the library breaks no caller of its own.

Test callers were updated too and are counted rather than listed: 12 call sites in

state.rs test module; 1 in the engine's public-tier tests; 10 execute call sites in the
engine's public-tier tests. No observer public-tier test calls advance_tick.
