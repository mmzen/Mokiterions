The request layout as built
==========================

WO-MOK-025's completion report item 6 asks for the shared block's token count, the actor block's, a
representative observation block's and enumerated set's, the resulting cacheable share as an
estimate, and which enumeration rendering was chosen with its measured cost, and it asks for the
plain statement that no cache ratio was measured. This file is that item.

Every figure comes from the transcript this repository commits, because SPEC-MOK-007 rule 11.3
carries the request as sent: blocks A and B in a prefix record, blocks C and D in each exchange
record. So a reader who distrusts this file can re-derive it from a file in the repository with no
build and no run. analysis/request-layout.py is the instrument, and its whole output is reproduced
below rather than summarised.

    RESULT: averaged over the transcript's 221 requests, the cacheable prefix is 87.16 percent of a
    request in bytes, ranging from 83.24 to 91.35. Every token figure in this file is an ESTIMATE
    derived from those bytes, because there is no tokenizer here and SPEC-MOK-006 rule 12.4 forbids
    adding one. NO CACHE RATIO WAS MEASURED, because no provider was called.

    RESULT: block D was built as one flat list of verb-target pairs, which is the first of the two
    shapes SPEC-MOK-007 leaves to measurement. The nested alternative was measured on the same 221
    sets and would save 5,469 bytes: 22.0 percent of block D and 0.40 percent of a mean request.

    FINDING, reported and not repaired: SPEC-MOK-007 rule 11.4.1 lists five characters that put
    block A outside the record stream's closed alphabet, and two of the five do not hold. Block A
    contains no parenthesis at all, and its full stops are inside that alphabet rather than outside
    it. The rule's conclusion is unaffected and is measured below. Rule 11.4.1 is approved text, so
    this is the repository owner's to settle.

--- Bytes are measured; tokens are estimated, and here the difference decides something ---------

SPEC-MOK-007 rule 3.5 states the cacheable share as an estimate in tokens and says so twice in one
sentence: "The cacheable prefix is **estimated** at 1,230 tokens of an **estimated** 1,430, which is
86 percent, against REQ-MOK-070's floor of 85." This file cannot improve on that in kind. It can
measure the bytes underneath it, and it does.

The reason a token measurement is unavailable is not effort. A provider's tokenizer is the
provider's, no crate may be added to either package (SPEC-MOK-006 rule 12.4, and this work order's
*Out of scope* repeats it as "**Any crate added to either package**"), and a hand-written tokenizer
would be a new correctness obligation whose output rule 14.4 refuses to accept anyway. The
specification's own counterexample says why in one line: a locally estimated ratio "can be 0.86 while
the provider charged for every token".

--- Block A: one string for the run, which is the whole basis of the cache order ----------------

5,385 bytes, 5,381 characters, and exactly ONE distinct value across all twelve prefix records.
That is rule 3.3 measured rather than restated, and rule 3.3 is not a preference: any variation
inside block A — "a name, a tick, a count, a whitespace difference" — destroys the shared prefix for
every request of the run, so the 87 percent above would collapse toward zero.

The one distinct value is a structural property here and not a lucky reading. Block A is a single
`const SHARED_RULES: &str = concat!(...)` at mokiterions-core/src/simulation.rs:1306, and the
comment at line 1419 records that the request type holds that constant rather than a composed
string, "so rule 3.3's byte-identity across a run is a property of the type". Two tests hold it:

  the_request_carries_four_blocks_in_the_cacheable_order
      rules 3.1 and 3.6. It asserts on blocks() rather than on a concatenation, and its own comment
      says why - a rotation of the four would keep a concatenation test passing.

  block_a_is_one_string_for_the_run_and_block_b_is_one_per_mokiterion
      rules 3.3 and 5.3, over a 20-tick run at seed 42, with an assertion that the run produced more
      than 100 requests so that the measurement is not vacuous.

--- Block A's one non-ASCII character, and the escaping that carries it verbatim ----------------

Block A's only non-ASCII character is U+2014 EM DASH, at character offsets 2,066 and 2,119. It is the
only non-ASCII character in any block: the census counts 24 in block A's twelve values, which is that
pair twelve times over, and zero in block B's twelve, block C's 221 and block D's 221. The two are a
matched pair around one parenthetical:

    Two Mokiterions at a distance
    of 1 or less — the same cell, or one of the eight cells around it — are in contact.

24 occurrences in the whole transcript, which is two per prefix record for twelve records and none
anywhere else. Rule 11.4.1 says block A "carries spaces, commas, parentheses, full stops and an em
dash"; that names the character rather than counting it, and the count is two.

  THE OTHER FOUR IN THAT LIST WERE COUNTED TOO, AND TWO OF THEM DO NOT HOLD. Block A carries 1,282
  spaces, 44 commas, 65 full stops, 2 em dashes, 90 newlines and NO PARENTHESIS OF EITHER KIND. So
  one of the five characters the rule names is absent from the block it describes. And a second does
  not do the work the list is there to do: the closed alphabet rule 11.4.1 quotes is
  `A-Z a-z 0-9 _ . - + : ; >`, which contains the full stop, so a full stop is not a character that
  puts block A outside it.

  The rule's conclusion is unaffected, and that is measured rather than assumed: spaces, commas, the
  em dash and the newlines are each outside that alphabet and each present, so block A is outside it
  many times over and rule 11.4.1's branch into an escaping function is the right branch. What is
  wrong is two items in a five-item list of evidence for a conclusion that three of the items already
  carry.

  It is not repaired here. Rule 11.4.1 is approved text — SPEC-MOK-007's amendment record carries it
  under the 2026-08-24 row, approved that day by the repository owner acting as accountable technical
  owner on six rulings taken over commit bfdbf71 — and an implementation agent may not amend an
  approved artifact. WO-MOK-025 stop-and-escalate condition 6 is what this is, and it is put to the
  owner with the work order's other open questions. The correction is one clause: strike
  "parentheses" and either strike "full stops" or move it out of the list of characters the alphabet
  excludes.

Rule 11.4.1 is the rule this matters to. The record stream's closed alphabet cannot apply to a
transcript, so the transcript takes SPEC-MOK-006 rule 3.4's other branch and arrives with an
escaping function, escape_transcript_text, whose obligation "is a round trip rather than an
alphabet". That was checked here rather than assumed: all 466 block values in the transcript —
twelve prefix records carrying two blocks each, 221 exchange records carrying two each — were
re-escaped by an independent implementation of the same three-plus-three rule and compared against
the bytes the transcript holds. 466 checked, 0 mismatches. The em dash is escaped by neither
implementation, which is why the block survives byte-identically.

The escape counts are the other half of that check, and they confirm the source's own claim. The
function's doc comment says the carriage return, the tab and the remaining control characters "are
not in any block today and the test beside this says so; they are handled anyway". Measured over the
transcript: 8,103 escaped newlines, and zero escaped quotation marks, backslashes, carriage returns,
tabs and control characters. So five of the six escapes the function implements are unexercised by
this transcript, and that is a fact about the data rather than about the function.

The one-byte spread is the tolerance's digit count and nothing else: five Mokiterions have a

--- Block D: which enumeration rendering was chosen, and what the other one would have cost -----

SPEC-MOK-007's *Explicitly unspecified decisions* leaves this open and states the trade-off:

    **The action grammar's shape.** Whether block D enumerates verb-target pairs as one flat list
    or as a verb list with per-verb target lists is unspecified, and the trade-off is left to
    measurement: a flatter list is longer and costs more variable tokens, a nested one is shorter
    and may be harder to answer well. Rule 7.1's completeness holds either way.

The flat list was built. One action per line, two spaces of indentation, under a header line, and
the largest of the 221 sets is 237 bytes at tick 13 for M04:

The measured cost of that choice is the second half of item 6, and it was measured rather than
argued. The instrument re-renders each of the 221 measured sets as the other shape — a verb, a
colon, and that verb's targets space-joined — and sizes both. The same set nested is 186 bytes:

    ACTIONS YOU MAY TAKE
      wait
      sleep
      move: north east south west
      attack: M01
      threaten: M01
      fight: M01
      retreat: M01
      surrender: M01
      approach: M01 M05 M02
      avoid: M01 M05 M02

Over all 221 sets: flat 24,911 bytes, nested 19,442, a saving of 5,469. That is 22.0 percent of
block D and 0.40 percent of a mean request. So the flatter list does cost more variable bytes,
exactly as the specification predicted, and the amount is four tenths of one percent of what is sent.

Two things follow, and only two. The cost side of the trade-off is settled: it is too small to buy
anything with. The other side is not settled by this file at all — whether a nested list is "harder
to answer well" is a question about a model's answers, and no model answered anything here. The
re-rendering above is a cost model and was never sent anywhere.

--- The token counts, as estimates, and the cacheable share ---------------------------------------

Item 6 asks for token counts. These are estimates, and the arithmetic is shown so that a reader can
substitute a different characters-per-token figure rather than take one on trust. Characters rather
than bytes, and the two differ by four in the whole request: block A's two em dashes cost three bytes
each where a character count counts one, and nothing else in any block is outside ASCII.

  block A  5,381 characters, in all twelve      block C  689.9 characters, mean of 221
  block B  39.6 characters, mean of twelve      block D  112.7 characters, mean of 221
                                                total    6,223.2 characters, mean request

At a uniform ratio the share does not move at all, because a uniform divisor cancels:

  3.5 characters/token   A 1,537   B 11   C 197   D 32   total 1,778   prefix share 87.1%
  4.0 characters/token   A 1,345   B 10   C 172   D 28   total 1,556   prefix share 87.1%
  4.5 characters/token   A 1,196   B  9   C 153   D 25   total 1,383   prefix share 87.1%

Against rule 3.1's diagram, which states about 1,200 tokens for A, about 30 for B and about 200 for
C: A lands on the diagram at 4.5 characters per token and C lands on it at 3.5, and B does not land
at all — the actor block estimates 9 to 11 tokens rather than 30, because it is three short lines and
40 characters. B is too small for that to move anything. Rule 3.5's 1,230 tokens for A and B together
is 2 percent above what A and B estimate at 4.5 characters per token, which is 1,205.

  THE ESTIMATE'S UNCERTAINTY IS LARGER THAN ITS MARGIN OVER THE FLOOR, AND THAT IS THE POINT.
  A uniform ratio is the wrong model here: block A is English prose and blocks C and D are
  identifiers, underscored words and integers, which tokenize more densely. Under a split ratio the
  share falls, because the denser blocks are the variable ones:

    A and B at 4.0, C and D at 3.5    prefix 1,355   variable 229   total 1,584   share 85.5%
    A and B at 4.0, C and D at 3.0    prefix 1,355   variable 268   total 1,623   share 83.5%
    A and B at 4.5, C and D at 3.0    prefix 1,205   variable 268   total 1,472   share 81.8%

  Two of those three are below REQ-MOK-070's 85 percent and one is above it. So this estimate cannot
  decide whether that floor is met, and no estimate made in this repository can. That is not a defect
  in the estimate; it is rule 14.4's reason, restated as a measurement.

--- No cache ratio was measured, because no provider was called -----------------------------------

Stated plainly, as item 6 requires: no cache ratio was measured. Nothing behind any figure in this
file called a provider, opened a socket, spawned a connector or read a credential. The 87.16 percent
above is a byte share of a composed request, and it is not a cache ratio and must not be quoted as
one.

The distinction is the specification's, not this file's caution. Rule 14.4: the ratio is "cached
prompt tokens divided by total prompt tokens, over the whole run, from the reported figures and
never from a local token estimate. A local estimate would let an implementation pass while paying
full price." Rule 14.8: "A replay spends nothing, computes no ratio and has no ceiling." And
REQ-MOK-070's own trigger is "WHEN a live model-backed run completes" — no live run has completed,
and none can be started under this work order, whose *Out of scope* includes the live-mode flag as a
user-facing option. The requirement is untriggered rather than unmet.

What does exist is the arithmetic that will consume a provider's figures, exercised against figures
the tests declare. the_cache_ratio_is_the_reported_figures_or_nothing holds three things: that 16,200
cached of 18,000 prompt tokens is 9,000 basis points; that one exchange reporting a prompt count with
no cached figure makes the run's ratio uncomputable for the remainder of the run, rather than
computable over the complete exchanges; and that a fallback, which reports neither figure, is not
that case. Every number in it is declared by the test, and the test's own comment says so.

--- What this file does not establish ------------------------------------------------------------

That the cacheable share is 86 or 87 percent in tokens. It is a mean 87.16 percent in bytes over 221
requests, and the token figures here are estimates whose spread crosses the floor they would be
compared against.

That the flat enumeration is the better of the two shapes. It measures the cost side and finds it
worth 0.40 percent of a request. The answer side needs a model.

That block D's direction filtering is correct. No position in this transcript is anywhere a
direction could be dropped, and the four-move enumeration in all 221 sets is a consequence of that
rather than a check of it. The suite's two block D tests are where that is held.

That block A's wording is right. Its constancy, its prohibitions and its required strings are held
by block_a_gives_no_strategy_and_names_nothing_that_varies; the prose itself is unspecified by rule 4
and is the implementation's.

Anything about another seed, density or horizon. Every figure here is the committed transcript's, a
20-tick run at seed 0 and density 0.75 in which all twelve Mokiterions act.
