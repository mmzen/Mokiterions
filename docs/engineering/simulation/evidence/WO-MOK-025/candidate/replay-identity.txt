The replay, and the two hosts
=============================

WO-MOK-025's completion report items 4 and 5 are what this file serves, and it serves both because
they are one measurement session: the same transcript is put through the engine's binary and through
the observer, and the refusals are the same refusals in both hosts because both hosts share one
parser.

Taken 2026-08-24 in the implementation tree on feature/phase-5-definition at commit 1854f7b, against
release builds of both binary targets. bce4229 is the last commit that changed a file under either
package, so these readings are of the same source at any later commit of this packet -
candidate/gates.txt states that measurement.

    RESULT, item 4: every replay of the committed transcript is byte-identical run to run and with
    and without a record sink; each of the seven mismatched configurations fails and names the
    mismatch, none leaves a partial record stream, and the one case that is not a mismatch - a run
    shorter than the transcript - completes with an empty standard error.

    RESULT, item 5: the observer replays the same transcript to tick 20, and its panes agree with the
    engine binary's own summary line in eight comparisons covering twelve figures, plus four
    positions and three actions. Three of REQ-MOK-077's obligations cannot be exercised at all,
    because the options that trigger them do not exist yet; they are named below rather than reported
    as passing.

Two record kinds and no third, which is SPEC-MOK-007 rule 11.2 as amended on 2026-08-24. There is

specification's own shape rather than an omission, and rule 12.3 is where the consequence is stated:
a transcript from a different seed, density or horizon is detected by the tick-and-actor check while
replaying, not by a declaration read up front. Cases R4, R6 and R7 below are those three, measured.
R7's horizon case surfaces through rule 12.4's transcript-exhausted path rather than through 12.3's
check, which is the same detection reached by the nearer rule.

--- Rule 19.7, checked rather than assumed -------------------------------------------------

Rule 19.7 reads: "No error message contains a credential, and no error message contains a path the
engine resolved, because the engine resolves none."

R3 and R3b are the two cases that put a path in a message, and the clause that matters is the
subordinate one. Both messages echo the argument the process received in argv, unchanged.

R3 was run from Git Bash with `/c/Users/mathi/...` and the message reads `C:/Users/mathi/...`, so
something converted it. That something is MSYS, before the process started: the conversion is in
argv, and the binary echoed argv. R3b was measured for exactly that reason, with a relative path that
MSYS does not touch, and its message is `does/not/exist.jsonl` character for character. So the
conversion is ruled out as an explanation of either message, and neither is a path the engine
resolved - the resolution happens in the
host - mokiterions-core/src/main.rs:85 and mokiterions-tui/src/main.rs:118 - and what crosses into
the library is an already-open reader. SPEC-MOK-007 rule 12.1.1 is what places it there, and the
comment above the observer's own call site states the connection to 19.7 in the source.

R4's message names a tick, an actor and two digests and no path at all. R6's and R7's name a tick and
an actor. No message in the eight cases contains a credential, and there is no credential to contain:
see the closing section.

  The observer's own run of it is disclosed rather than presented as clean. The observer has no
  non-interactive exit - nothing ends the program but a key press, and on Windows crossterm reads
  the console input buffer rather than the standard input handle, so keys cannot be piped in. It
  was measured: keys written to the process's standard input were not read, and the run continued
  until it was killed. The capture is therefore taken by letting the run reach the horizon and then
  killing it, so the process exit status is 124 (the killer's) and not 0. What establishes that the
  run finished is the frame, which says `finished tick_limit` and `tick 20`.

The capture is reproducible in spite of that. Three separate runs produced byte-identical standard
output, 27,948 bytes each, and identical reconstructions:

    sha256 4a5e19c6005663c4165e40345e2e86a687eaa81db19203de9501fdc21d2cb71d, all three

The stream converges because the observer stops redrawing once the run is finished, so the last frame
is the same frame however long the process is left alive past the horizon.

--- Which panes the observer's run exercised ------------------------------------------------

Two answers, because the capture above and the suite reach different panes.

In the capture, at the viewport the process was given: the header, the two territory summary rows,
the roster pane, the view pane and the footer were all drawn and all carry content -
candidate/observer-screen.txt is 30 rows of it. The log and the inspector were not drawn, and the
header says why in its own words: `overlays: log L at height 38  inspector i at width 140`. At this
size the observer announces both as overlay-only, which is SPEC-MOK-003's existing behaviour and not
something this source changed.

The suite reaches all six, at a viewport where layout::resolve places every optional pane on the
screen. mokiterions-tui/tests/replay.rs::the_observer_replays_this_source_to_the_horizon_with_every_pane
is VER-MOK-018 case L31, and it is a differential against `social` at the same seed for the same five
ticks rather than an assertion under this source alone. Its own printed line, from
cargo test -- --nocapture at this commit:

    the observer reached tick 5 under both sources over 60 answered opportunit(ies); panes
    PaneReport { tick: 5, roster_accounts_for_every_living: true, map_drew: true,
    log_presented: true, inspector_names_the_selection: true, filter_narrows: true,
    filter_label: "event=world_initialized", exported: true } ; footer "seed 42  ticks 5
    density 0.75%  source llm  tick 5  events 258"

Six panes, each read from its own region of the drawn buffer rather than off the screen, each
non-vacuous, and each equal to what it is under `social`. The export is the sixth: the export key
wrote a non-empty file where the operator asked.

  What L31 does not do is open a transcript. Its port is a scripted stub, and the test file's own
  header says so and says why - Proposer is the engine's one interface for a decision from outside
  itself, this host cannot tell a stub from a reader-backed port, and what a real port does with a

  path through the real ReplayPort over a real file is exercised by this file's captures and by no
  automated test. That is stated again in the closing section, because it is the one coverage gap
  this measurement session found.

--- REQ-MOK-077's refusals that could not be exercised --------------------------------------

Three of REQ-MOK-077's obligations have no exercise at this commit, and the reason is the same for
all three: the option that triggers them does not exist in either host.

  Required response 3 - "In the terminal observer, asked for a live run - by a connector path, a
  live-mode selection or a spend ceiling - refuse before the terminal is entered, exit with the
  invalid-configuration status, and state on standard error that this host replays only."

  Failure and boundary behavior, second bullet - "The observer is given a connector path. It
  refuses with a diagnostic. It does not accept the option and act on nothing."

  Acceptance example, failure behavior - the observer given the transcript and a connector path
  exits 2 before entering the terminal and "writes to standard error that this host replays only
  and that a live run is the engine binary's".

What the two hosts accept today, from their own usage lines:

  Mokiterions        --seed --ticks --policy --density --trace-actions --events-path
                     --transcript-path --help
  mokiterions-tui    --seed --ticks --policy --density --transcript-path --speed --start-paused
                     --export --help

No connector path, no live-mode selection and no spend ceiling in either. Measured rather than read
off the usage text: `connector-path`, `--live`, `spend-ceiling` and `max-spend` each appear zero
times in either package's src/. The two occurrences of `live-mode` are both inside one comment block,
at mokiterions-core/src/cli.rs:301 and 304, which states the position in the source itself - "Under
this work order there is no live-mode selection at all, so the condition is unconditional;
`WO-MOK-026` adds the selection and this check gains its second term rather than moving."

This is WO-MOK-025's own scope and not a shortfall. Its Out of scope section names "The live-mode
flag and the spend-ceiling option as user-facing options" and "The connector, its protocol
implementation and the canned connector".

  What can be said about the three, measured: the observer given any of the three option names today

--- No provider was called, and there is nothing to call it with -----------------------------

SPEC-MOK-007 rule 12.2: "A replay makes no provider call, opens no socket, spawns no connector and
reads no credential. This holds whether or not a credential is present in the environment, and it
holds in both hosts."

This is not a network measurement and is not offered as one. What was measured is the surface that
would be needed to make a call, over both packages' src/ at the candidate:

    process::Command   0        TcpStream     0        std::net    0
    Command::new       0        TcpListener   0        reqwest     0
    env::var           0

The engine package's [dependencies] table is empty. The observer's holds two entries, the engine by
path and ratatui. Neither package can open a socket or spawn a process without one of the names above
or a crate that has one, and it has neither.

The suite's own case is a_refused_replay_names_no_provider_and_no_credential, and
the_committed_transcript_carries_no_credential_and_no_conversion reads the committed file for the
same thing. Both pass at this commit; candidate/gates.txt is the whole suite reading.

--- What this file does not establish -------------------------------------------------------

That the observer's transcript-reading path is covered by an automated test. It is not. The
observer's public tier uses a scripted port by design and states why; the engine's tier reads the
transcript. The wiring between them - mokiterions-tui/src/main.rs opening the file and handing over a
ReplayPort - is exercised by this file's captures, and a capture that has to be killed is weaker
evidence than a test. It is named here so that a reviewer weighing L31 knows what L31 covers.

That the reconstruction is a terminal emulator. It honours cursor positioning, carriage return and
newline and discards every other escape sequence. analysis/observer-screen.py states the assumption
and the failure mode, and the eight-figure agreement with the engine's summary line is the
independent reading that makes the reconstruction trustworthy rather than assumed.

That the observer replays every seed. It replays one, at one horizon, from the one transcript this
repository commits. The engine's five declared seeds in both tracing selections are the suite's ten
cells, quoted above.

That a live run works, in either host. Nothing in this file runs one, and nothing in this repository
can: there is no connector.
