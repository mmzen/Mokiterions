1. Why this is a short file and not a second full packet
--------------------------------------------------------

The candidate packet's thirteen readers measure two 120-cell captures. A merge that changed the streams
would invalidate every figure read from them and would owe all thirteen again. This merge does not
change them, and section 2 is that measurement rather than that assertion: the merged tree's own
capture is byte-identical to the candidate's on all 120 cells and all four columns.

The precedent this follows is WO-MOK-019's merge/second/, which established its own carry-forward
licence with two empty diffs -- one half of that merge was byte-identical to master and the other to its
own chain. **Neither empty diff is available here**, and the difference matters enough to state: master
rewrote about two thousand lines of mokiterions-core/src/simulation.rs for the record stream while this
branch corrected the non-waste condition inside the same file, so both halves of this merge are genuinely
merged text. The licence is therefore the output equality of section 2, which is measured on the streams
the packet's figures are read from, and it is weaker in exactly one way that section 5 makes explicit:
it says nothing about source-level claims.

**check_declared_dependencies.py is the check the pull request never ran.**
.github/workflows/dependency-declarations.yml is `pull_request`-only, and no `pull_request` run has

`if: github.event_name == 'pull_request'` and were skipped with it. Two green checks on the PR, neither
of which read the work-order trailer, the preflight or the dependency graph. Running the repository's
own program locally is not a substitute for the run -- it is the same program on the same tree, but the
merge commit GitHub would test is its own -- and the push that carries this merge is what makes the
`pull_request` run fire. That the local run passes is recorded here so that a red check, if one
appears, is known to be about the prospective merge rather than about this tree.
