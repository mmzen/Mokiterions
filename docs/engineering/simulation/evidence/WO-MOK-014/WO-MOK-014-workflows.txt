VER-MOK-013 — both placements, and the search for a restated declaration
========================================================================

Work order   WO-MOK-013 (crates policy, declared-set comparison)
Branch       governance/adr-mok-006-third-party-crates
Date         2026-08-20

SPEC-MOK-005 rule 15.5 requires the release gate and the pull-request gate to read one
declaration rather than two copies of one. VER-MOK-013 makes that checkable: search both
workflow files for every crate name, version and feature name in either declared set. This
file is the search, and the files it searched.

The terms are not typed out below. They are read out of SPEC-MOK-002 rule 13 and SPEC-MOK-003
by the same parser the checking program uses, so this search cannot be looking for a
declaration different from the one being checked — which a hand-written term list would be the
first time a declaration was amended and the list was not.

     1  # Compare each package's resolved dependency graph against the set its specification declares.
     2  #
     3  # This workflow is repository-owned and implements `SPEC-MOK-005` rule 15, which places the four
     4  # checks of rule 8.4 -- 8.4a, 8.4b, 8.4c and 8.4d -- at pull-request time as well as at the
     5  # release gate. A dependency graph drifts between commits in a way formatting does not: an
     6  # undeclared crate, a feature switched on by unification, or a lockfile update that pulls in a
     7  # prohibited capability all arrive with an ordinary-looking diff. Rule 15.1 wants those to fail
     8  # where they are cheap to fix rather than on release day.
     9  #
    10  # What this workflow deliberately does NOT do:
    11  #
    12  #   * add the format, lint or test checks to pull-request CI -- rule 15.2 keeps this scope
    13  #     narrow. Those live at the authorized commit under rule 8 and in retained evidence at the
    14  #     candidate commit, and rule 15 changes neither placement.
    15  #   * touch `engineering-harness.yml` -- rule 15.3. That file is managed, listed in
    16  #     `.engineering-harness.lock` with a schema-2 SHA-256 lock, verified by
    17  #     `python -m se_harness doctor`, and its `governor` job would report an edit as tampering.
    18  #     This workflow is added beside it and the managed file is not modified.
    19  #   * approve anything -- rule 15.4. It is evidence, not authority. It can refuse a merge and it
    20  #     approves nothing. Whether a crate belongs in a declared set is `ADR-MOK-006`'s question
    21  #     and the technical owner's answer, recorded in a specification and not in CI.
    22  #
    23  # It runs the same program the release gate runs, `scripts/check_declared_dependencies.py`, which
    24  # reads the declared sets out of `SPEC-MOK-002` rule 13 and `SPEC-MOK-003` and restates neither.
    25  # Rule 15.5 is the reason: an implementation that duplicated a declaration would be a third
    26  # source of truth, and the two placements could then disagree about what is declared while both
    27  # reported success. Amending a declared set changes this workflow's verdict with no edit here.
    28  #
    29  # It fails closed. Every refusal names the fact it could not establish.

declared set changes both verdicts with no edit to either file, which is the property rule 15.5
asks for, and it is a property of the text rather than a claim in a comment.

`check_declared_dependencies.py`: five hits, all in two term lists and one sentence.

  * `mio` at line 664 and `ratatui` and `crossterm` at lines 690 sit in `PROHIBITED_TERMS` and
    `USER_INTERFACE_TERMS`. These are prohibitions, not declarations: the list says which names
    8.4d refuses in the engine's graph or reports as a transitive hit, and it carries no version,
    no feature set and no count. `ratatui` is in it because REQ-MOK-026 confines the user
    interface to the observer -- the term exists so that `ratatui` in the *engine* refuses, which
    injection case 10 demonstrates. A term list written from ADR-MOK-006 decision 4's capability
    classes is the opposite of a copied declaration: it was deliberately not derived from the
    present graph, which is why it hit two crates nobody had looked at.
  * `quote` at line 1046 is the English verb, in a sentence about quoting artifact prose. It
    collides with the build-script crate `quote 1.0.47` and means nothing.
  * `10` is again "rule 10".

An earlier draft of that file did carry 57, 63 and 62 in its module docstring, explaining what
8.4a does not compare. That sentence was rewritten to point at SPEC-MOK-003 instead, because a
count in a comment is a second copy of a declaration and the copy in the code is the one that
goes stale. This search is what found it.

`test_check_declared_dependencies.py`: 76 name hits, 48 version hits, 46 feature hits, 12 figure
hits, and this is deliberate and disclosed rather than clean.

Its reading tests parse the real SPEC-MOK-002 and SPEC-MOK-003 out of the checkout and assert
today's values -- one entry, `ratatui 0.30.2`, the counts 57/63/62/66, the build-script table's
7/9/9 with `winapi 0.3.9` on Windows and not on Linux, and the two disclosures outstanding. Its
injection tests build synthetic declarations out of the same names, because a fixture that reads
like the real thing is a fixture a reader can check.

So an approved amendment to a declared set edits this file too, and this is the only place in
the repository where that is true. It is not a second declaration -- nothing reads these
assertions to decide whether a graph conforms, and the gate would refuse on a real mismatch
whatever they said -- but a reader who took "amending a declared set needs no code edit" as
unqualified would be wrong about the test suite. The file's own docstring now says so, and
VER-MOK-013's *What an admission must retain* list is where the obligation belongs.

The alternative was to rename every fixture crate to a synthetic name so that no declared value
appeared in any script. That buys a clean search result and costs the reading tests, which are
the ones that catch an amendment renaming a heading or writing a *Features* cell the convention
cannot parse. The failure mode those tests exist for is the one a hand-copied declaration hides,
and it is worth more than a tidy grep.
