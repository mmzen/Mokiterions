## A regression this check found, and the fix
#
  The conformance check is that *every* command form in the repository's documentation resolves.
  Sweeping the repository for `cargo run` found two places using the bare form, and the bare form
  no longer works:

    $ cargo run -- --help
    error: `cargo run` could not determine which binary to run. Use the `--bin` option to specify
    a binary, or the `default-run` manifest key.
    available binaries: Mokiterions, mokiterions-tui
    exit=101

  This is a real regression introduced by this work order, not a pre-existing defect. Before the
  change the repository root was the engine package, so `cargo run` at the root had one binary to
  choose from and ran the engine. The root is now a virtual manifest over two packages, each with a
  binary, and Cargo refuses to guess.

  `SIMULATION_RULES.md` had seven bare invocations: one in section 12 and six in section 15's
  "Running it yourself" block. All seven were changed to `cargo run --bin Mokiterions`, and section
  15 gained two sentences saying why the flag is there and naming the other program, since the
  guide is written for a reader who should not have to infer it. Nothing else in the guide changed.

  The alternatives were considered and rejected. `default-run` is a `[package]` key and a virtual
  manifest has no package, so it cannot be set at the root. `[workspace] default-members =
  ["mokiterions-core"]` would make the bare form resolve, but it would also make bare `cargo test`
  and bare `cargo clippy` apply to the engine alone — which is precisely the CI defect this work
  order exists to remove. Naming the binary in the documentation is the only fix that does not
  reintroduce it.

## An approved contract that would no longer resolve, disclosed and not edited
#
  `VER-MOK-001` step 1 reads "Run `cargo run -- --seed 42 --ticks 100`". That step would now fail
  with exit 101 for the reason above. It is not edited, for two reasons. `VER-MOK-001` is an
  approved verification contract that was discharged against its own commit, where the bare form
  did resolve; editing a discharged contract would misrepresent what was verified then. And
  amending an approved contract is the assurance owner's act under `DECISION_RIGHTS.md`, not this
  work order's. The observation is carried to the completion report and the verification record.
  The engine's behaviour under that step is unchanged and re-measured in
  `comparison/engine-matrix.txt`; only the way it is invoked would need a `--bin`.

## The other launch instructions in the repository
#
  `README.md` contains no `cargo` invocation at all. `scripts/` and `.github/workflows/` contain
  none either — the harness scripts are Python and PowerShell and invoke no Cargo command. Every
  `cargo` form in `docs/engineering/` outside `VER-MOK-001` already names its target explicitly
  (`--bin Mokiterions`, `-p Mokiterions`, `-p mokiterions-tui`), which is why those artifacts needed
  no correction. `docs/engineering/REPOSITORY_CONTEXT.md` was amended, because it describes the
  layout itself and the layout is what changed; `amendment-approvals.md` records that amendment and
  its approval.
