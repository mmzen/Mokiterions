# Per-tick cost: wall clock for the declared long run, before and after
#
# VER-MOK-017's per-tick cost check: "Measured as wall-clock for a declared long run before and
# after, reported as a figure rather than as an assurance, with the measurement's own variance
# stated."
#
# Platform: Windows 11 Home 10.0.26200; cargo and rustc 1.97.1; the release profile; one process
# at a time; wall clock rather than CPU time, so the spread includes whatever else the machine was
# doing. Seven repetitions per configuration, each reporting every repetition, the mean, the
# median, the extremes, and the spread as a percentage of the mean.
#
# The run is --policy individual --ticks 6600 --start-paused, driven to the engine's own end. It is
# the same run O8 uses and the longest this work order declares.
#
# The driver is `15-per-tick-cost-driver.rs`, retained beside this file. It is not part of either
# commit: it is copied to `mokiterions-tui/tests/timing.rs` in each tree for the measurement and
# removed afterwards, and it reaches the observer only through items that were already public
# before this work order, so the same file compiles against both trees. It times `advance` alone and
# draws no frame, because accumulation happens as a tick's records are ingested.
#
# The measurement did not come out as a clean before-and-after pair, so it is reported as the series
# that was actually run. What the first two configurations alone would say is wrong, and the reason
# is stated below the captures.
#
# Configurations
#
#   A  the candidate, default release profile
#   B  the base commit ccb0584, default release profile
#   C  the candidate with every accumulation path disabled, default release profile
#      - `self.accumulate_decisions();` wrapped in `if false`, and the `TerritoryCrossed` and
#        `AttackResolved` arms of `ingest` guarded by `if false`; nothing else touched
#   D  the candidate's src/state.rs with the base's src/render.rs, default release profile
#   E  the candidate tree with both changed sources replaced by the base's, default release profile
#   F  the candidate, codegen-units = 1
#   G  the base commit ccb0584, codegen-units = 1
#
# C, D and E are substitutions on the candidate tree, applied for the measurement and reverted
# immediately; C's patch is reproduced at the end of this file. F and G are the same two trees as A
# and B with CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1 in the environment and nothing else changed.
#
# Configuration D's transcript carries three `never used` warnings, and they belong there rather than
# being a defect in the candidate. D pairs the candidate's `src/state.rs` with the base's
# `src/render.rs`, so the accumulation exists and nothing presents it: `ActionKind::ALL` and `label`,
# the five `Profile` accessors with `absorb`, and the three `Observer` accessors have no caller in
# that pairing. The candidate itself is clean, and `02-lint-candidate.txt` is the transcript that
# says so - clippy at `-D warnings` from a cleaned tree, exit 0. No warning appears in A, B, C, E,
# F or G.
#
# ==== the engine alone, for scale ====
#
# The engine binary at 6600 ticks, three runs at each tree, timed with a wall clock around the
# process. The two binaries are byte-identical, per `08-engine-output-unmoved.txt`, so this is a
# scale figure and not a comparison:
#
#   candidate      run 1: 0.1299 s, 19.685 us per tick
#   candidate      run 2: 0.1068 s, 16.187 us per tick
#   candidate      run 3: 0.1129 s, 17.111 us per tick
#   base ccb0584   run 1: 0.1102 s, 16.694 us per tick
#   base ccb0584   run 2: 0.1015 s, 15.375 us per tick
#   base ccb0584   run 3: 0.1035 s, 15.684 us per tick
#
# So roughly 16 us of each per-tick figure below is the engine's own work, and the rest is the
# observer's - overwhelmingly the world snapshot it takes after every tick, which this work order
# does not touch.
#

# ==== What the series measures ====
#
# The figures, mean per tick:
#
#   A  candidate, default profile                               266.3 us
#   B  base, default profile                                    153.0 us
#   C  candidate, accumulation disabled, default profile        262.6 us
#   D  candidate state.rs, base render.rs, default profile      159.6 us
#   E  candidate tree, both sources from base, default profile  154.4 us
#   F  candidate, codegen-units = 1                             243.6 us
#   G  base, codegen-units = 1                                  250.1 us
#
# A against B looks like a 74% regression. It is not one, and three configurations say so:
#
#   C. Disabling every accumulation path in the candidate leaves the figure at 262.6 us, inside the
#   spread of A's 266.3 us. If the accumulation were the cost, removing it would have recovered it.
#
#   D. Restoring the base's `src/render.rs` while keeping the candidate's `src/state.rs` with the
#   accumulation live gives 159.6 us, which is the base's figure. The driver draws no frame, so no
#   line of `src/render.rs` executes in this measurement at all, and a file that is never called
#   cannot cost 100 us per tick.
#
#   E. The candidate tree with both changed sources replaced by the base's gives 154.4 us, so the
#   working tree, its target directory and the platform are not the variable either.
#
# What is left is the compiler. The release profile defaults to sixteen codegen units, and which
# unit a function lands in decides whether its callers can inline it. Adding roughly 130 lines to
# `src/render.rs` re-partitions the crate, and the hot path here - `Observer::advance` and the
# engine snapshot it copies - loses an inlining decision it happened to win before. F and G remove
# that variable: at codegen-units = 1 the candidate is 243.6 us and the base is 250.1 us, a 2.6%
# difference against spreads of 9% to 13%, with the candidate the faster of the two.
#
# The measured conclusion, as a figure rather than an assurance:
#
#   With the codegen partition held fixed, the accumulation's per-tick cost is below this
#   measurement's resolution: 243.6 us against 250.1 us over 6600 ticks, a difference smaller than
#   the run-to-run spread of either configuration. An upper bound of about 25 us per tick - one
#   spread - is all this instrument supports. It cannot report a positive figure, because it cannot
#   separate the accumulation from noise.
#
#   Under the default release profile the candidate measures 266.3 us per tick against the base's
#   153.0 us. That difference is real for anyone running this build, and it is reported here rather
#   than suppressed; C, D and E establish that its cause is codegen partitioning rather than
#   accumulation, since it survives removing the accumulation and disappears on restoring a file the
#   measured path never calls.
#
# Two things this does not establish, stated rather than left implied:
#
#   1. It does not establish that the default-profile figure is unimportant. Anyone looking at the
#   observer's frame budget has a real 113 us per tick to account for, and the place to look is the
#   partitioning, not the totals.
#
#   2. It does not measure drawing. Presenting fifteen figures costs something per frame, and this
#   instrument times `advance` only. The bound that matters for drawing is structural instead: a
#   frame reads the retained records and formats fifteen integers, with no iteration over the event
#   buffer and no allocation per figure.
#

#
