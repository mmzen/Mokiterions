# Layout and viewports — WO-MOK-005

`SPEC-MOK-003` rule 5 as amended 2026-08-19 places each optional pane on one threshold in
the one axis that constrains it. Every figure below is read from a resolved layout or from
a drawn in-memory buffer; none is asserted from the specification's text. That holds of the
fixed figures the tables below derive from as well — they are read from the layout resolved
at the 160 x 48 reference viewport:

  header           3 rows
  footer           1 row
  roster           47 columns
  inspector        44 columns
  log              10 rows where both of its thresholds are met, otherwise 6

## Each pane's threshold, measured on both sides

Each row is `layout::resolve` at the two adjacent sizes the threshold separates, taken at
every value of the other axis in the sweep's range rather than at one chosen size. A row
holds when the pane is absent at every size on the low side and present at every size on
the high side.

pane        threshold             absent below it        present at and above it   across
roster      W >= 100              99 x H     39/39       100 x H     39/39         H = 22..=60
inspector   W >= 140              139 x H    39/39       140 x H     39/39         H = 22..=60
log         H >= 38               W x 37     167/167     W x 38      167/167       W = 34..=200

The taller log answers to both axes at once, so it is measured as a triple rather than as a
row:

log rows    W >= 140 and H >= 48  140 x 48 -> 10 rows   140 x 47 -> 6 rows   139 x 48 -> 6 rows
                                  either threshold alone leaves the log at 6 rows

## What each canvas addresses

The canvas interior is the view pane less the one cell its border occupies on each side.
In overview zoom one character cell carries a 2 x 4 braille dot grid, so the world region a
canvas addresses is twice its width by four times its height, clamped to the 128 x 128
world. Each row is `spatial::Viewport::resolve` over the resolved canvas, camera at the
origin:

160 x 48    canvas  67 x 32    world region 128 x 128   x0-127 y0-127   whole world yes
160 x 44    canvas  67 x 32    world region 128 x 128   x0-127 y0-127   whole world yes
160 x 40    canvas  67 x 28    world region 128 x 112   x0-127 y0-111   whole world no
140 x 44    canvas  47 x 32    world region  94 x 128   x0-93  y0-127   whole world no
140 x 43    canvas  47 x 31    world region  94 x 124   x0-93  y0-123   whole world no
120 x 48    canvas  71 x 36    world region 128 x 128   x0-127 y0-127   whole world yes
120 x 30    canvas  71 x 24    world region 128 x 96    x0-127 y0-95    whole world no
100 x 30    canvas  51 x 24    world region 102 x 96    x0-101 y0-95    whole world no
 34 x 22    canvas  32 x 16    world region  64 x 64    x0-63  y0-63    whole world no

The world appears whole where the canvas reaches 64 columns and 32 rows. The smallest
viewports that reach them, found by resolving every width and every height rather than by
arithmetic — the horizontal answer depends on which panes stand beside the view:

horizontal, roster and inspector placed     W >= 157
horizontal, roster placed, inspector not    W >= 113
vertical, at 160 columns                    H >= 44

## Monotonicity over the plane

Rule 5's monotonicity obligation: for two viewports above the floor with W' >= W and
H' >= H, every pane present at W x H is present at W' x H'. Checked by resolving every
size in the range below and comparing it with its wider and its taller neighbour, which is
sufficient because the relation is transitive over single steps.

range            W = 34..=200, H = 22..=60
adjacent pairs   13026
panes checked    roster, inspector, log
violations       0

Canvas area is deliberately not monotone, and rule 5 declares each place it is not. The
three crossings, measured as the canvas rows or columns they cost:

inspector arrives    139 x 47  -> 140 x 47    canvas 90 x 35 -> 47 x 35
log grows to ten     140 x 47  -> 140 x 48    canvas 47 x 35 -> 47 x 32
log arrives          160 x 37  -> 160 x 38    canvas 67 x 31 -> 67 x 26

## Negative control: the superseded tier table

A case that cannot fail proves nothing, so the same three checks are run against the rule
that shipped: `tier_for` and the per-tier pane match transcribed from
`mokiterions-tui/src/layout.rs` at commit 05dc6ac, the predecessor of the amendment. The
transcription borrows the fixed rows and the pane widths from the resolved layout above,
because the amendment changed neither.

The three threshold rows, run again against the superseded table. A pane whose presence the
table made conditional on the other axis holds at only some sizes on the high side, and the
count says at how many:

pane        threshold   present above it, as amended    the same, superseded
roster      W >= 100    100 x H  39/39                  100 x H  23/39
inspector   W >= 140    140 x H  39/39                  140 x H  17/39
log         H >= 38     W x 38   167/167                W x 38   40/167

On the low side the two rules agree, so nothing here is an argument that the superseded
table placed panes too eagerly. What it did was withhold panes the viewport had room for:

roster      W < 100     99 x H   absent 39/39
inspector   W < 140     139 x H  absent 39/39
log         H < 38      W x 37   absent 167/167

                                    rule as amended        superseded tier table
monotonicity violations             0                      12   of 13026 pairs
declared viewports disagreeing      0                      4   of 9

The superseded table's monotonicity violations, first six of 12:
  roster 139x38 -> 140x38
  log 139x38 -> 140x38
  roster 139x39 -> 140x39
  log 139x39 -> 140x39
  roster 139x40 -> 140x40
  log 139x40 -> 140x40

The declared viewports it would have resolved differently:
  160 x 40    superseded: no roster, no inspector, no log   canvas 158 x 34    as amended  67 x 28
  140 x 43    superseded: no roster, no inspector, no log   canvas 138 x 37    as amended  47 x 31
  120 x 30    superseded: no roster, no inspector, no log   canvas 118 x 24    as amended  71 x 24
  100 x 30    superseded: no roster, no inspector, no log   canvas  98 x 24    as amended  51 x 24

Those rows are two different things. The reported defect, where the viewport had room for
every pane and the tier table matched no row at all:

  160 x 40
  140 x 43

A viewport 140 columns or wider and short of 44 rows fell to the table's `otherwise` and
lost the roster, the inspector and the log at once. The monotonicity pairs above are that
same fault as the operator met it: growing a terminal by one column took a pane away.

And the rows where no defect is involved and the amendment's substance is what changed the
answer:

  120 x 30
  100 x 30

The superseded table withheld the roster from a viewport with the columns for it because the
same row also demanded rows for the log. Placing each pane on the axis that constrains it
leaves a wide short terminal its roster and costs it only the log.

## The one-below-floor refusal

The floor is the one part of rule 5 the 2026-08-19 amendment does not touch, and it is
measured again here to show that: `layout::below_floor` refuses 33 x 21 and admits 34 x 22
exactly as it did before.

below_floor(33, 21)   true
below_floor(34, 22)   false

The refusal itself is carried forward unchanged from the 2026-08-18 capture, where it was
produced by the real start-up path, before the terminal is entered, so a terminal too small
to observe in is never altered. Reproducing it needs a real terminal of that size: the
start-up path reads the size from the operating system and treats a size it cannot read as
no refusal at all, so a captured run under this oracle would prove nothing. The message and
the exit code are asserted by the internal test named below.

$ mokiterions-tui            # in a 33 x 21 terminal
exit code 2
standard output: 0 bytes
standard error:
viewport error: the terminal is 33 x 21; the observer requires at least 34 x 22

At the floor itself, 34 x 22, start-up is accepted: an observer is returned, nothing is written
