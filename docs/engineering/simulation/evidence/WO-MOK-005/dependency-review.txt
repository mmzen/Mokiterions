# Dependency and boundary evidence — WO-MOK-005

Re-derived against the merged tree. The engine package keeps the name `SPEC-MOK-002` rule 1
fixes, `Mokiterions`, so every command below names that package rather than a renamed one.

Re-captured on 2026-08-19. Nothing this work order does touches a dependency, and no figure
below changed: 61, 59, 57 and 37 crates by the four readings, 182 `Cargo.lock` entries, three
`serde` names in the lockfile and none in the resolution, and the same two build-only crates.
What changed is where the engine package lives — `WO-MOK-006` moved it into
`mokiterions-core/` — so every path cargo prints is different, the engine manifest is read at
`mokiterions-core/Cargo.toml`, and the observer's path dependency now reads
`{ path = "../mokiterions-core" }`. The observer's manifest also gained the `[lib]` target that
work order added. A path that no longer resolves makes a check unrepeatable even when its
answer is still right, which is why the commands were re-run rather than annotated.

### Why the lockfile is larger than the compiled surface, and why 'serde' appears in it

`Cargo.lock` records the maximal resolution: every optional dependency of every resolved package,
whether or not the feature enabling it is on. `serde`, `serde_core` or `serde_derive` is listed there as
an optional dependency of the packages named below. The observer enables none of those features, so no
serde crate appears in the resolved graph above and none is ever compiled.

$ grep -n '^name = "serde' Cargo.lock
1126:name = "serde"
1136:name = "serde_core"
1145:name = "serde_derive"

packages in Cargo.lock whose dependency list mentions serde:
  ratatui-core, ratatui-widgets, ratatui, wezterm-input-types, time

The figure that matters for the containment claim is the resolved graph, not the lockfile:
`cargo tree -p Mokiterions` is a single line, so nothing in the lockfile reaches the engine.
