    at 7fa037b, clean worktree                       ff6c1b54f6f465d0e2f6b0d54e681663a87258b4eb07aeb075faed61afc88680

Editing evidence prose does not move it: the generator reads the typed artifacts under
`docs/engineering/`, and an evidence file carries no frontmatter and is not one, which the first two
lines measure. Committing does move it, because the snapshot embeds the revision it was generated
at — `repository.revision` in `target/harness-dashboard/dashboard-data.json` is `HEAD`, and each
entry of its `revision_provenance` array carries an `observed_revision` field that is also `HEAD`.

So the digest is commit-bound by construction, and that is what makes it provenance rather than a
checksum of the artifact set: a record naming a digest names the tree the digest was taken at. The
consequence for this packet is that a verification record must name the digest measured at the
commit it binds itself to, not one measured earlier. `VREC-MOK-005` carries its own commit and
digest in its frontmatter, and this file deliberately does not restate them: a value written here
would have to be measured before this file's own commit, and so could not be the value the record
needs.

One thing follows from that and is worth stating plainly, because it looks like an error and is not:
the commit that *adds* the record to the tree is necessarily a child of the commit the record
*names*. `harnessctl capture-verification` reads `HEAD`, writes the record file, and then that file
has to be committed, so no record can name its own commit. A reviewer who regenerates the dashboard
at this branch's head will therefore read a third digest and see this record reported with
`match_state: different`, exactly as `VREC-MOK-001` through `VREC-MOK-004` are already reported. The
record binds the tree that was verified, not the commit that files the record about it.
